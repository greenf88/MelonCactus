# Preview storage provenance — 2 October 2026

Internal technical evidence for [draft PR #15](https://github.com/greenf88/MelonCactus/pull/15), not a production measurement or legal consent decision. Cookie names are recorded, but no values, message content, request IDs or authenticated screenshots are in this repository.

## Scope and sources

- **Owner observation:** Edge DevTools screenshots on 2 October 2026, with the protected MelonCactus preview domain selected. This was the owner's observation, **not** a network/storage capture by Codex. The previously shown genuine EN/NL contact pageview POST bodies and displayed `Referer` remain evidence only for those requests; no contact form was submitted.
- **Loaded-script observation:** the authenticated preview page listed `/e3ffe1d2b830bc05/script.js` and `https://vercel.live/_next-live/feedback/feedback.js` as script elements. The latter is the Vercel Toolbar/feedback URL. A separate read-only download of that **same URL** exposed the code cited below; it was not a byte-for-byte capture of the authenticated browser response. A separate request for the preview Analytics script returned the protection HTML rather than JavaScript, so its actual browser-delivered body and response headers were not inspected.
- **Project/package inspection:** no exact observed key names were found in `src/` or the installed `@vercel/analytics` and `next` packages. The site's [`PrivacyAnalytics`](../../src/components/privacy-analytics.tsx) uses `@vercel/analytics/next` with a `beforeSend` public-path allowlist and URL query/fragment removal. This source check does **not** establish who set a cookie server-side or what every production request contains.
- **Provider context:** [Vercel Toolbar](https://vercel.com/docs/vercel-toolbar) is enabled by default on previews; [Deployment Protection](https://vercel.com/docs/deployment-protection) authenticates protected deployment requests; [Web Analytics](https://vercel.com/docs/analytics) says its visitor identification uses a request-derived hash, not Analytics cookies. These product descriptions are not a substitute for a response-header capture.

The owner inventory did **not** cover `vercel.live` as a separate origin, IndexedDB, all cookie attributes, or all `Set-Cookie` responses. A public fetch of the preview Analytics script did not pass deployment protection, so its script body and server-side cookie behaviour remain uninspected. No protection setting was changed or bypassed. The absence of exact names in the site and installed Analytics package, together with Vercel's no-Analytics-cookie description, gives **no positive evidence** that site Analytics sets or reads any listed key. It is not a proof that all Analytics or hosting processing is storage-free.

## Decision boundary

The owner-shown pageview bodies and `Referer` close the earlier payload/referrer question **for the displayed EN/NL contact requests**. The preview storage inventory is now recorded for the selected origin; it should not remain listed as wholly unobserved. Unresolved attribution of `vercel-feature-flags`, missing `Set-Cookie`/attribute history and uninspected other-origin storage do not by themselves establish an Analytics leak or demand a site-code change. They do prevent a blanket claim that the preview, let alone production, is cookie-free. Assess Analytics consent against the actual processing and applicable rules; do not infer it from a cookie list alone. After separately approved publication, measure production requests, headers and storage in a normal public browser before finalising a production-specific statement. No synthetic Analytics POST or contact submission was used.
